# B43 - Restored backups now belong to gold_migrator + backup/restore guide

## Why
`restore.sh` loaded the dump as the `postgres` user, so every restored table/function was owned by `postgres`. Later updates run migrations as `gold_migrator`, which cannot alter objects it does not own - a restored database would have failed the *next* migration. Found by checking ownership after a restore in a test database.

## Changes
- `deploy/scripts/restore.sh`: loads the dump with `set role gold_migrator`, so ownership matches a normal install.
- New `docs/deployment/10-backup-and-restore.md`: routine, taking/downloading backups (correct scp for PowerShell and Git Bash), laptop restore, production restore, monthly practice restore.

## Tested / untested
Tested: ownership result in a plain PostgreSQL test (without it: owner `postgres`; with `set role`: owner the intended role, extensions and schemas restore fine). Not tested: the real Docker run - on your laptop do a restore (guide section 4) and then run `docker compose up -d --build` once to confirm the migrate step is happy, and check:
```
docker compose exec db psql -U postgres -d gold -c "select distinct tableowner from pg_tables where schemaname='gold'"
```
Expected: only `gold_migrator`.
If you already restored a backup on any machine with the old script, fix that database once: re-run the restore with the new script.

# B42 - Scripts no longer depend on the "executable" flag

## Why
On Windows Git does not reliably keep the executable flag of shell scripts (it can be lost on commit, pull or reset, and shows up as "changed" files in VS Code). Twice it broke things: CI `database` job ("Permission denied", exit 126) and `./scripts/update.sh` on the server. Fighting the flag on Windows is a losing game, so nothing now needs it.

## Changes
- `.github/workflows/ci.yml`: runs `bash ./backend/db/run-tests.sh ...`.
- `deploy/scripts/update.sh`: calls `bash ./scripts/backup.sh`.
- Guides 04, 05, 06, 07, 08, 09 and notes: scripts are run as `bash ./scripts/<name>.sh` (works whether or not the flag is set).
- `deploy/db-init/00_roles.sh` needs nothing: the database container runs or sources it either way.

## After it is merged: on the SERVER, once
The nightly backup cron line calls the script directly; make it independent of the flag too:
```
crontab -l | sed 's#&& \./scripts/backup\.sh#\&\& bash ./scripts/backup.sh#' | crontab -
crontab -l
```
The line must now read `... && bash ./scripts/backup.sh >> backups/backup.log 2>&1`.
From then on install updates with `bash ./scripts/update.sh`.
