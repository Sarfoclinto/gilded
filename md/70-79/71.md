# B71: automatic backups, an encrypted copy off the server, a weekly restore check, and alerts (v1.19.2)

Your choice: the off-site copy goes to Backblaze B2 (or any S3). Server-side only: a new `backup` service in `deploy/docker-compose.yml`. No database, API, web or desktop change.

## Why
Backups were made by hand (`scripts/backup.sh`), kept on the same Hetzner machine, never checked, and nothing reminded anyone to run them. If that disk failed, the database and every photo were gone.

## What it does now
- **Every night at 01:30 (Ghana time)**, the database is copied into `deploy/backups`, checked to be readable, and the newest 7 copies are kept on the server.
- **An encrypted copy goes off the server** once the bucket is set up. The database copy and every photo are sent, encrypted with your passphrase first, so Backblaze only stores scrambled files and names. Photos travel once. A personal picture someone deleted is deleted there too. Old copies are tidied: nightly ones for 35 days, the copy from the 1st of each month for 400 days. After each upload the size in the bucket is compared with the copy.
- **Every Sunday at 03:15**, the newest copy is loaded into a scratch database. The main tables are compared with the live one, then the scratch database is removed. This proves the backups can really be put back.
- **Failures are told.** If the backup or the check fails, directors (everyone who may change company settings) get a notification in the app, in plain words.
- **Status.** `deploy/backups/status.json` holds the last run, result, size, off-site and the last check, ready for a system-status page later.
- **Getting it back.** `offsite list`, `offsite fetch <file>` and `offsite fetch-photos` bring copies back from the bucket. `scripts/restore.sh` then puts the database back, as before.
- **Refuses to leave unencrypted.** With a bucket set but no passphrase, nothing is sent, and the directors are told.

Full guide for setting up Backblaze and restoring: `deploy/BACKUPS.md`.

## What you need to do
1. Create a private B2 bucket and an application key limited to it (BACKUPS.md, steps 1–2).
2. Fill the `BACKUP_*` lines in `deploy/.env` (new in `.env.example`), including a long passphrase. **Keep a copy of the passphrase away from the server.**
3. `docker compose up -d --build backup`, then `docker compose exec backup backup-now` and `docker compose exec backup offsite list`.
4. Once, on a spare machine: practise the "new server" restore in BACKUPS.md.

## Tested here
The scripts were run for real on this machine: PostgreSQL with the test database, rclone, and a local folder standing in for the B2 bucket, through the same encryption layer.
- **A normal night.** The copy is made and checked, sent and size-matched; the photos are sent. In the bucket, nothing is readable: no file name, no SQL, no photo bytes.
- **Retention.** The newest 2 kept locally when the setting is 2; the off-site copies all present.
- **Restore check.** It loaded the copy and compared six tables with the live database (all equal), then removed the scratch database.
- **Off-site recovery.** A copy fetched back from the bucket is identical (same SHA-256), and the photos were fetched back into an empty folder.
- **Failures.**
  - With no passphrase, nothing was sent, the job failed, and directors were notified.
  - A damaged newest copy failed the check, and directors were notified.
  - With the database unreachable, the failure is recorded (no notification possible, see limits).
  - A good run clears the error.
- **Scheduler setup.** The two schedules were written, and the settings file is readable by its owner only (crond was replaced by a stand-in).

## Not tested here
- **Building the container.** Docker Hub is blocked from this machine, so the image (Alpine 3.21 with `postgresql17-client` and `rclone`) was not built. Build it on the server first.
- **Real Backblaze.** The bucket was a local folder. Do steps 3–4 above.
- **busybox crond itself** firing at 01:30. Check `docker compose logs backup` the next morning, and `status.json`.

## Limits
- If the database is down, no in-app notification can be sent. A system-status page (on the plan) would show the last good backup.
- If the backup service is stopped, nothing runs and nothing is said. Check `docker compose ps`.
- The weekly check needs free disk for one more copy of the database while it runs.
