# B38 - Fix: queued purchases and payments were rejected ("Enter the customer name")

## Cause
Since B30 a signed device sends its queued commands to /sync/commands. For a purchase, that path handed the screen's raw body (customerName at the top) straight to the database function, which wants the worked-out form built by TransactionPlanner (customer nested, items recalculated, payments split). So every purchase from a signed device was "rejected" with "Enter the customer name", never saved, and the detail page showed 404 because no purchase existed. My earlier database test fed the already-worked-out form, so it did not catch this. Queued payments (transaction.pay) had the same kind of mismatch (transactionId vs id). Drawer movements and exchanges were already in the right shape.

## Fix
- SyncService now prepares each command the way the normal save does: purchases go through TransactionPlanner (with the company's formula settings), payments are converted to the database shape.
- If that check fails, the entry is still recorded as rejected for a manager, with the real reason (migration 0049 adds "planError" to gold.sync_apply), instead of reaching the database in a shape it cannot read.
- ISyncStore.CalcConfigAsync (new), PostgresOperationsStore.ParseCalcConfig shared, SyncService takes IClock.
- Tests: db/tests/043_sync_plan_errors.sql (passes with all 43 database tests), three new SyncServiceTests (purchase worked out; invalid purchase recorded with reason; payment shape).
